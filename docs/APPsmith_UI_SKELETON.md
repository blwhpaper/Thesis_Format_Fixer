# Appsmith UI 骨架说明

## 1. 目标

本轮只建立“论文格式工具”应用骨架，先验证：

- 页面分区是否清晰
- 普通用户是否容易理解
- 三层结果语义是否明确
- 未来接入真实 API 时是否有清晰落点

不做：

- 真实 Python 修复引擎联调
- 真实批量处理能力
- 生产级工作流

## 2. 页面结构

页面骨架定义见：

- `appsmith/skeleton/page_blueprint.json`

可视化预览见：

- `appsmith/preview/index.html`
- `appsmith/preview/styles.css`
- `appsmith/preview/app.js`

页面从上到下分为七块：

1. 顶部应用标题与模式切换  
   用户在这里理解应用用途，并在“检查模式 / 修复模式”之间切换。

2. 单文件处理卡片  
   放置文件选择、开始处理、重置等核心操作。

3. 批量处理卡片  
   本轮先做占位，为后续目录上传、批量队列和汇总结果预留空间。

4. 结果摘要卡片  
   以用户可读方式展示三层结果，不暴露内部技术字段名。

5. 详细问题表格  
   展示逐项问题，便于用户定位和处理。

6. 产物下载区  
   展示修复文档、检查报告、用户摘要等产物入口。

7. 人工复核说明区  
   汇总重点问题与建议下一步，避免用户只看表格却不知道优先处理什么。

## 3. 三层结果语义

摘要区严格按以下三类展示：

- 已自动修复  
  指系统已经直接完成的项目，用户通常只需抽查。

- 检测到异常但未自动修改  
  指系统已经识别问题，但出于安全和准确性考虑，没有直接改动原文。

- 需人工复核  
  指即使已做检查或局部处理，仍需要用户结合学校模板、导师要求或论文上下文进行确认。

## 4. 表格字段

详细问题表格当前固定包含：

- 规则编号
- 问题标题
- 所属区块
- 严重级别
- 是否自动修复
- 处理建议

这些字段均为普通用户可读表达，避免直接暴露内部工程字段。

## 5. mock 联动说明

`appsmith/preview/app.js` 会根据页面状态加载不同 mock：

- `empty-result.json`
- `check-result.json`
- `fix-result.json`
- `failure-result.json`

联动规则：

- 切换“检查模式”时默认切到检查成功态
- 切换“修复模式”时默认切到修复成功态
- 手动切换页面状态时，摘要、表格、下载区、人工复核说明同步更新
- 空状态下隐藏表格主体，仅显示引导文案
- 失败状态下保留统一摘要区，但产物区回落为空提示

## 6. 为真实 API 预留的位置

本轮已为后续真实 API 预留清晰位置：

- 单文件卡片中的“开始处理”按钮  
  后续绑定 `POST /api/jobs/check` 或 `POST /api/jobs/fix`

- 页面状态与结果区  
  后续绑定 `GET /api/jobs/{job_id}` 的返回值

- 产物下载区  
  后续绑定下载地址字段

- 批量处理卡片  
  后续扩展为批量接口或前端串行队列

## 7. 建议的 Appsmith 页面组件映射

建议在 Appsmith 中按如下思路落地：

- `Container`：页面主分区
- `Button Group` 或多个 `Button`：模式切换
- `FilePicker`：单文件上传
- `Button`：开始处理 / 重置 / 下载
- `Table`：详细问题表
- `Text` / `RichText`：摘要与人工复核说明
- `List` 或 `Container`：产物下载区
- `Collapsible`：批量处理说明或次级帮助信息

## 8. 下一步对接建议

下一轮最合理的接续动作：

1. 先确认 Docker Desktop 可用并把 Appsmith 真正拉起
2. 在 Appsmith 中创建应用并按本骨架搭页面
3. 接入仓内现有 `thesis-format-fixer-api`
4. 先打通单文件 `check`
5. 再接单文件 `fix`
6. 最后再做批量处理真实链路
